#1. 왜 FRotator 대신 FBoneTransform(FQuat)을 써야 하는가?

언리얼 엔진의 FTransform은 내부적으로 회전을 오일러 각(Euler Angle)인 FRotator(Pitch, Yaw, Roll)로 표현합니다. 여러 포즈를 합성할 때 매 합성마다 FQuat $\leftrightarrow$ FRotator 변환을 거치면 두 가지 치명적인 문제가 발생합니다:

❌ 1. 짐벌 락(Gimbal Lock) 및 각도 왜곡

오일러 각은 특정 축이 90도에 도달하면 자유도를 잃습니다. 또한 359도와 1도가 만날 때 358도를 회전하는 플립 현상이 발생합니다.

✅ 2. FBoneTransform 도입을 통한 해결

회전을 순수 4원수 FQuat 상태로 보존하는 FBoneTransform을 생성하여 모든 가중치 누적을 마친 후, 최종 출력 시점에만 NormalizeRotation()을 거쳐 변환합니다.

#2. 쿼터니언 최단 경로(Shortest Path) & 부호 반전(Sign Flip)

4원수 $q$와 $-q$는 3차원 공간에서 완전히 동일한 회전을 나타내는 이중 덮개(Double Cover) 특성을 갖습니다. 그러나 두 쿼터니언을 단순히 가산($q_1 + q_2$)할 때 부호가 다르면 360도 반대 방향의 먼 경로를 돌거나 포즈가 상쇄되어 버립니다.

// Accumulate 모드에서의 부호 정렬(Bias) 연산
FQuat SourceQuat = GetBoneRotation(Source);
const float Bias = (SourceQuat.Dot(Dest.Rotation) >= 0.0f) ? 1.0f : -1.0f;
Dest.Rotation += (SourceQuat * (BlendWeight * Bias));

두 쿼터니언의 내적(Dot Product)이 음수이면 180도보다 먼 각도를 돌고 있다는 뜻이므로, Bias = -1.0f를 곱해 부호를 반전시킨 후 가산함으로써 항상 최단 경로(Shortest Path) 회전을 보장합니다.

#3. N개 포즈의 가중합: Overwrite $\rightarrow$ Accumulate 패턴

언리얼 엔진은 3개 이상의 포즈를 블렌딩할 때 첫 번째 포즈로 버퍼를 초기화하고(Overwrite), 이후 포즈들을 누적(Accumulate)하는 템플릿 패턴을 사용합니다.

// 1. 첫 번째 포즈의 가중치로 덮어쓰기 (기존 쓰레기값 제거)
BlendPose<ETransformBlendMode::Overwrite>(SourcePoses[0], TempAtoms, SourceWeights[0]);
// 2. 나머지 포즈들을 순차적으로 누적
for(int32 PoseIndex = 1; PoseIndex < NumPoses; ++PoseIndex)
BlendPose<ETransformBlendMode::Accumulate>(SourcePoses[PoseIndex], TempAtoms, SourceWeights[PoseIndex]);
// 3. 최종 정규화 및 패킹
for(int32 BoneIndex = 0; BoneIndex < NumBones; ++BoneIndex) {
TempAtoms[BoneIndex].NormalizeRotation();
ResultPose[BoneIndex] = TempAtoms[BoneIndex].ToTransform();
}

#1. 조화 평균(Harmonic Mean)을 사용하는 이유

Foot Sliding 방지 핵심 공식

걷기(1.2초)와 달리기(0.6초)를 50:50으로 섞을 때, 단순 산술 평균을 취하면 $\frac{1.2 + 0.6}{2} = 0.9$초가 됩니다. 하지만 애니메이션 길이는 시간의 개념이며, 캐릭터의 이동성은 속도($v = \frac{1}{T}$)에 비례합니다.

// 1. 각 애니메이션의 초당 루프 속도(속력 역수)를 가중 평균
float BlendedNormalizedSpeed = (1.0f / WalkLength) * 0.5f + (1.0f / RunLength) * 0.5f;
// 2. 합성된 속도의 역수를 취해 최종 블렌딩 길이를 도출
float BlendedLength = 1.0f / BlendedNormalizedSpeed;
❌ 산술 평균 (Arithmetic Mean)

$0.5 \times 1.2 + 0.5 \times 0.6 = 0.90\text{초}$

발걸음 속도가 실제 가중치와 맞지 않아 발이 바닥에서 미끄러지는 현상 발생.

✅ 조화 평균 (Harmonic Mean, 언리얼 방식)

$\frac{1}{0.5/1.2 + 0.5/0.6} = 0.80\text{초}$

이동 주파수(Frequency)가 물리적으로 선형 비례하여 발걸음이 지면에 정확히 고정됨.

#2. 정규화 시간(Normalized Time) 위상 동기화

SequencePlayer는 초(Seconds) 단위로 시간을 누적하지만, BlendSpacePlayer는 길이가 다른 애니메이션들의 왼발/오른발 타이밍(위상)을 맞추기 위해 0.0 ~ 1.0의 정규화 시간(Normalized Time)을 누적합니다.

// 1. 정규화된 시간 누적기 전진 (0.0 ~ 1.0)
InternalTimeAccumulator += (DeltaTime * PlayRate) / BlendedLength;
if (bLoop) while(InternalTimeAccumulator >= 1.0f) InternalTimeAccumulator -= 1.0f;
// 2. 각 샘플마다 자신의 실제 초(Seconds) 단위 시간으로 역산하여 전달
for(FBlendSampleData& Data : BlendSampleDataCache) {
const FBlendSample& Sample = BlendSpace->GetBlendSample(Data.SampleDataIndex);
Data.Time = InternalTimeAccumulator * Sample.GetSamplePlayLength();
}

이렇게 하면 InternalTimeAccumulator = 0.5일 때, Walk는 0.6초 위치(오른발 착지), Run은 0.3초 위치(오른발 착지)가 추출되어 두 동작의 발걸음 위상이 완벽하게 일치한 상태로 합성됩니다.
